## Prioritized findings register

Evidence vocabulary: **reproduced** = executed an isolated probe/browser check; **code-confirmed** = the behavior follows directly from inspected code, without changing production; **investigate** = a plausible issue requiring additional validation. Priorities: P1 correctness/data or workflow blocker; P2 reliability/usability; P3 maintenance/improvement. No issue below implies that historical training data was altered.

### A01 — P1 — Referenced canonical games stop accepting actual results — code-confirmed

`src/live/current_season.py::_upsert_mutable_game` calculates changed fields, then returns immediately whenever player stats, team stats, or live predictions reference the game. This avoids the previous DuckDB FK exception but also discards later score, played/status, date, and venue changes. A prediction made before a game can therefore prevent the canonical row becoming final. Fix narrowly: keep stable IDs and no-op detection; update safe changed scalar fields without rewriting parent FK/provenance columns. Test with referenced games, changed scores, and a repeated identical refresh. Do not delete children or drop FKs.

### A02 — P1 — Availability decisions depend on a team but generated predictions are shared — code-confirmed risk

`src/control_center/service.py::optimize` automatically protects current-roster/FORCE_INCLUDE unknown players as PLAY and defaults other unresolved players to OUT. That resolved prediction run is stored without a team-profile policy identity, while all three team slots read the latest shared run. A later team can inherit assumptions made for another roster. BUILD_NEW also protects the existing roster. OUT participates in teammate-minute redistribution, so this is a modeling assumption, not only a candidate filter. Make the policy explicit and fingerprint it; either use roster-independent scenarios or isolate scenario selection per team without sharing incompatible runs.

### A03 — P1 — Automatic availability retry can reuse stale unresolved IDs — code-confirmed risk

The retry in `service.py::optimize` checks the old run's market batch but can reuse its unresolved IDs after newer manual availability overrides. Its generated explicit PLAY decisions can then compete with newer OUT evidence. Rebuild unresolved candidates from current resolved availability before writing a decision file; never let automatic fallback supersede an explicit current override. Needs an isolated override/retry test.

### A04 — P1 — Saved recommendation contract loses identity and strategy — reproduced / code-confirmed

`repository.py::latest_run` returns flat market/prediction fingerprints and recommendations, but omits the nested `snapshot` contract used by `app.js::recommendationMatchesCurrent`, current input roster, optimization mode and strategy details. The browser only compares nested fingerprints and season/matchday. Probe confirmed that a changed roster still matches. Reload can accept stale recommendations and lose strategy/mode information. Restore a versioned full response (or an equivalent explicit database projection), and compare saved roster, bank, constraints, scenario and profile as well as data fingerprints.

### A05 — P1 — Injured owned players can block the attempt to sell them — code-confirmed risk

`_load_live_pools` in `scripts/optimize_fantasy.py` excludes non-SCORED/OUT players. Current-team validation is then performed against this filtered pool. An unavailable owned player can be reported as missing from the market, preventing transfer optimization. Validate ownership/prices against the full official market; apply availability restrictions only to incoming/retained candidates. Test a valid team owning one OUT player.

### A06 — P1 — Threaded HTTP requests mix incompatible DuckDB connection modes — investigate

`src/db/database.py::connect_database` opens either read-only or read-write connections to the same file; `ThreadingHTTPServer` can overlap these. Read API paths also materialize price forecasts and bootstrap saves state. DuckDB rejects simultaneous connections with different configurations. Reproduce in a temporary database, then design one consistent application connection policy and serialize writes. Do not solve by changing production read-only audit access into writes.

### A07 — P1 — Refresh marks returned prediction failure as success — code-confirmed

`service.py::refresh` unconditionally adds a SUCCEEDED prediction step whenever the prediction runner returns. The runner also returns terminal statuses such as AVAILABILITY_UNRESOLVED and MODEL_ARTIFACT_MISMATCH without raising. The UI can say everything refreshed successfully despite unusable predictions. Interpret the returned status and preserve meaningful failure/retry details. Similarly inspect stage-result handling in the live pipeline.

### A08 — P1 — Frozen strategy artifact no longer matches runtime source — reproduced

`tests.test_phase8c.test_phase8c_version_and_frozen_phase7_artifact_are_unchanged` fails in `validate_phase7_artifact`: `Phase 7 code artifact mismatch: scripts/optimize_fantasy.py`. The control-center path and CLI validation are inconsistent. Do not merely rewrite hashes to silence the check: separate adapter/UI changes from frozen strategy code or explicitly version and validate the intended deployment contract. Check dependent manifests before changing any file listed in them.

### A09 — P1 — Prediction selection can drift during an optimization — code-confirmed risk

The service selects and fingerprints a prediction context, but `_load_live_pools` independently queries the latest successful/partial run. Concurrent regeneration could make the pool differ from the recorded snapshot. Pass the selected prediction-run ID through the whole call chain and reject incompatible readiness/scenario states. `_prediction_current` also does not itself require `production_ready`; inspect interaction with global rules/scoring gates before changing it.

### A10 — P1 — Shadow advice may not follow the recommendation actually applied — investigate

`shadowMatchesCurrent` checks season/matchday only. Shadow code chooses BEST_OVERALL, whereas the UI allows applying other recommendations. Verify that the applied recommendation, actual saved roster and team profile are all bound to the shadow/after-turn advisor. Current team switching retains old bootstrap shadow fields. Advice for a different selected roster must not appear current.

### A11 — P2 — Team switching can race an in-flight bootstrap — code-confirmed

`switchActiveTeam` does not increment `loadEpoch`; an older bootstrap can complete after a new team context and overwrite it. `applyTeamContext` updates state/roster/constraints but retains previous-team `latest_shadow_snapshot`, `latest_advisor`, `latest_recommendation` and dashboard. Add request identity tied to slot, invalidate pending loads and clear/reload profile-specific context. Test delayed responses and a failed switch; preserve drafts and the previous team's state on failure.

### A12 — P2 — Freshness queries can see future events — code-confirmed

`src/live/freshness.py::source_freshness(as_of=...)` computes age relative to as_of but does not restrict captured_at in its SQL. A backdated evaluation can select future refreshes and produce negative ages. Add a timestamp cutoff and test historical reads. Events also aggregate globally across seasons; document this limitation or include relevant season/source identity.

### A13 — P2 — Prediction currentness does not capture all new evidence — code-confirmed risk

`_prediction_current` checks stored generation-time freshness, market batch and manual overrides. It does not compare the current freshness of every required source or preparation/cache versions. New preparation evidence with an unchanged market may leave old predictions marked current. Introduce source/version fingerprints and explicit invalidation; avoid silent regeneration from read endpoints. Validate actual current-feature content before asserting a live snapshot is stale.

### A14 — P2 — Recent-five history is not a complete live timeline — code-confirmed

`repository.py::player_recent_form` reads historical ML targets plus preparation rows. New canonical current-season EuroLeague games outside the materialized historical targets can be absent. It has no explicit as-of cutoff, so attaching recent form to old snapshots could include later evidence. Unify the display query over actual historical/live results plus preparation with date/artifact cutoff, match deduplication, and deterministic ordering. Preserve the historical training tables unchanged.

### A15 — P2 — Partial preparation boxes can yield misleading result/FP confidence — code-confirmed risk

History preparation scoring infers team scores by summing player points. Incomplete player boxes can make that result/win bonus wrong. Live preparation scoring uses stricter completeness requirements and can therefore use minutes while History displays only a conservative FP estimate. Store/consume verified team scores separately, retain missing-stat metadata, and distinguish reported PIR/VAL, reconstructed FP and lower-bound estimates. Never fill missing fouls drawn/blocks received with zero. The recent-five chips currently discard some of this confidence metadata.

### A16 — P2 — Preparation provenance/dedup/update gaps — code-confirmed risk

Preparation IDs are based on source and source game ID, permitting the same real match from different providers. Updates can overwrite known starter/stats with null and do not consistently update all game tags/provenance. A feature fingerprint based only on IDs/artifact IDs may miss in-place corrections. Add cross-source match identity and change fingerprints; preserve non-null observations unless a documented correction replaces them. No re-ingestion during this audit.

### A17 — P2 — Recommendation cards overflow at tablet widths — reproduced

Chromium at 768px: document scroll width 828px; player metrics reach x=815. At 1100px: document width 1102. Existing narrow-screen rule only fixes smaller phones. The card's 155px + 250px minimum columns cannot fit inside two-column position/transfer groups. Use container-aware stacking/flexible tracks; verify 390/768/1100/1440px and actual card bounds. Screenshots are in `audit_2026-09-23/optimization-before-*.png`. Player table overflow is intentionally inside a scroll container and should not be confused with this defect.

### A18 — P2 — Missing numeric predictions become real zeroes in helpers — reproduced

`expectedRole({expected_minutes:null})` returns BENCH / LIMITED; `fpPerMinute({fp_per_minute:null, expected_fp:20, expected_minutes:25})` returns 0 instead of 0.8. JavaScript Number(null) is zero. Use a shared finite optional-number conversion and preserve UNKNOWN/N/A. Audit quick comparisons and totals for the same issue without changing prediction values.

### A19 — P2 — HTTP validation and unknown API contracts are incomplete — code-confirmed risk

Unknown GET `/api/...` paths fall through to SPA HTML 200. Negative Content-Length is not rejected before read; JSON accepts nonfinite numbers and some state validation only compares `<0`. Return structured 404/400 and reject nonfinite credits/counts and oversized/negative body lengths. Inspect local mutation origin/content-type policy and request timeouts; prioritize actual localhost usage without inventing a remote deployment requirement.

### A20 — P2 — Demo no longer implements all frontend routes — reproduced

Browser demo receives 500 for `/api/strategy/current` and `/api/history`; team-context support also needs review. New frontend workflows have outgrown the demo service contract. Extend in-memory fixtures or return an explicit supported empty state; never connect demo to production data as a shortcut.

### A21 — P2 — UI and demo disallow zero transfers — reproduced / code-confirmed

The service state permits zero and optimizer supports keeping a team. UI clamps transfer count to 1..11 and demo rejects zero. Existing zero-transfer test fails. Align validation and labels with the backend; distinguish building a team from transfer-limited improvement.

### A22 — P2 — Team slot keyboard navigation is incomplete — code-confirmed

Inactive team tabs have tabindex=-1 but no roving arrow-key handler, making them unavailable in normal keyboard navigation. Add Left/Right/Home/End behavior or use ordinary accessible buttons. Preserve tab semantics and focus across renders.

### A23 — P2 — History limits and player detail need clearer scope — code-confirmed / improvement

Queries use fixed limits (e.g. 250 rows / 100 player games) without pagination/truncation notices. Preseason player links enter canonical EL history without a merged preparation timeline, and stale filters can yield confusing emptiness. Expose limits and scope, preserve missing values, and label displayed fantasy credits as current-market prices rather than game-time prices.
